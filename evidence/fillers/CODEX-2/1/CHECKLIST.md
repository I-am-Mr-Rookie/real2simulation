## Confirmed acceptance defect

- [ ] **P2 — verifier accepts incorrect service and status labels.** `infra/railway/dev/verify.py:25-33` checks HTTP code, revision and readiness dependencies, but not JSON `service` or `status`. `offline-observations.json` proves the actual verifier exits0 with all10 checks passing when every health/version response claims `service=WRONG-SERVICE` and `status=WRONG-STATUS`. Require exact service/status semantics per endpoint; add wrong-service, wrong-status and missing-field rejection cases. Keep worker-ready503 accepted only with heartbeat unavailable.

## Release-readiness boundaries (intentional, not new vulnerabilities)

The leaf also guards independently. Pure owner-policy success is not authenticated HTTP success. ## Operational/security hardening checklist (no exploit established)

- [ ] **Dependency-pool isolation and recovery.** `Build/api/health/dependencies.py:14-15,69-99` bounds response waiting, not underlying task duration. Three synthetic blocked probes leave another app instance's dependency queued and unavailable without calling its adapter. Receipt proves in-process contention only, not cross-service starvation: deployed API and worker are separate processes, normally with one health instance each. DNS can outlast socket limits; the existing README already acknowledges this. Retain fail-closed responses and no-duplicate scheduling; later verify recovery, concurrent requests and real resolver limits before stronger bounded-operation claims.
- [ ] **Dev-only gating has a documented local exception.** `dependencies.py:71` accepts absent `RAILWAY_ENVIRONMENT_NAME` when `R2S_ENVIRONMENT=development`; fresh replay confirms a probe runs. README explicitly permits unset Railway context for local dev, so this is **not** a discovered contract violation. Deployment acceptance must nevertheless prove the explicit target environment; never infer Railway-dev provenance solely from this guard. Decide separately whether a future deployment mode should require both markers.
- [ ] **Builds are not fully reproducible.** `infra/railway/dev/web.Dockerfile:1-7` uses a mutable image tag and `npm install`; stage.py allowlists package.json/src only. API/worker Dockerfiles likewise use mutable Python tags and top-level requirements without transitive locks. Direct version pins and committed-context hashes do not freeze dependency trees or base images. Future packaging scope: commit/allowlist appropriate lock artifacts, deterministic installs and image provenance. No vulnerability scan/CVE conclusion or dependency change was made here.
- [ ] **Web frozen-revision evidence is weaker than API/worker.** API/worker Dockerfiles embed source revision and expose `/api/version`; web has neither comparable revision endpoint nor source ARG. `verify.py:34-44` verifies HTML strings/status only and defaults to the historical deployed SHA for other services (`:8`). For any future candidate, separately prove web deployment/source association and intentionally update expected revision; this task authorizes no candidate/deploy changes.
